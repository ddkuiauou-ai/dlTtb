## 3. A — 기준과 테스트 환경 준비

### 웹

- 홈과 활성 카테고리 경로의 현재 동선을 기록한다. 첫 화면, 중간, append 직전/직후, 끝, 위로 복귀, 상세 복귀를 포함한다.
- 저장소의 실제 `PostGrid`·`InfinitePostList` 및 필요한 provider를 사용하는 테스트 전용 화면을 만든다. production에서 노출되지 않게 한다.
- 이 화면은 `queries.ts`의 업무 조회함수를 호출하지 않는다. 실제 Home/JSON 생성의 rotation 쓰기 부작용을 브라우저 반복 시험에서 격리한다.

- IDB·local/session storage는 테스트용 피드 키와 생성 버전으로 격리한다.
- 현재 DOM에 남은 글만 검사하지 않는다. 고정 높이 모델과 같은 폭의 비가상화 기준 렌더를 이용해 **예상 가시 ID 목록**을 독립적으로 구한다.

현재 웹에는 SQL 소스 문자열 검사 3개만 있고 브라우저 자동 시험 설정은 없다. 기존 브라우저 도구로 실제 화면을 검증하되, 반복 가능한 회귀를 위해 Playwright 등 브라우저 시험 설정을 별도 작은 변경으로 추가하는 것을 권장한다. 이는 앱 라이브러리 일괄 업데이트와 분리한다.

- 전용 fixture PostgreSQL을 우선 사용한다. 기존 `is_runtime` fixture는 `is_test_<UUID>` schema를 만들고 해당 schema만 사용한 뒤 정리한다.

- 실제 업무 DB의 view 정의와 schema를 읽기 전용으로 확인하고 fixture/source 정의와 비교한다. `CREATE ... IF NOT EXISTS`만으로 기존 MV 정의가 갱신된다고 가정하지 않는다.

## 4. B — 공통 가상화 수정

주요 위치: [infinite-post-list.tsx](/Users/craigchoi/silla/is/components/infinite-post-list.tsx), 필요 시 [post-grid.tsx](/Users/craigchoi/silla/is/components/post-grid.tsx). 큰 컴포넌트 전체를 다시 쓰지 않고 위치 측정 등 필요한 책임만 작은 hook/함수로 분리한다.

### B1. 좌표를 같은 변경에서 맞춘다

- 자동 모드의 margin은 목록 root의 `getBoundingClientRect().top + window.scrollY`로 계산한 문서 시작 위치다.
- 가상 행은 `virtualItem.start - effectiveScrollMargin`으로 배치한다.
- `getTotalSize()`를 이중 보정하지 않는다.
- 기본 자동 측정과 명시적 숫자 override를 지원한다. 실제 문서 시작점인 경우의 숫자 `0`도 유효하다. 기존 `auto`가 0으로 변환되는 경로를 제거한다.
- sticky header 높이는 문서 시작 위치와 별개로 정렬·가시 영역 계산에 사용한다.
- 위치·열 수 준비 상태를 명시하여 직접 페이지 접근/복원이 잘못된 초기값으로 시작하지 않게 한다.

### B2. 앞쪽 높이가 바뀌면 위치를 갱신한다

- 목록 자체의 크기뿐 아니라 앞쪽 섹션 또는 적절한 레이아웃 컨테이너의 변화도 관측한다. 크기는 그대로이고 위치만 이동하는 경우를 포함한다.
- 스켈레톤→카드, 빈 데이터, 반응형 열 수, 이미지·폰트 로딩 시 실제 위치를 다시 읽는다.
- 알림은 한 animation frame에 합치고 동일 좌표에서는 state를 갱신하지 않는다. StrictMode/재마운트 cleanup으로 observer·listener 중복을 막는다.
- 초기 예약 공간은 레이아웃 안정화에 사용하되, 해당 높이가 항상 맞는다는 전제는 두지 않는다.

### B3. 위치 갱신과 행 높이 캐시를 분리한다

- margin만 달라지거나 뒤에 페이지가 추가될 때 기존 행 높이 캐시를 유지한다.
- 설치 버전에 없는 `measureRange`를 기대하고 전체 `measure()`로 대체하는 경로를 정리한다.
- 새 DOM 행은 정상적인 `measureElement` 경로로 측정한다.
- 열 수/카드 모양 변화로 행 구성이나 크기가 달라질 때는 필요한 재측정을 수행한다. 이때도 읽던 글 ID를 기준으로 위치를 유지한다.
- custom `scrollToFn`은 라이브러리의 `adjustments`와 스크롤 옵션을 반영한다. 가능하면 설치 버전의 기본 window scroller를 사용하고, custom이 필요한 이유가 있을 때 계약을 완전히 지원한다.

### B4. 앵커 정책과 복원 동선을 검증한다

- 최신 목록을 읽는 중에는 글 ID와 화면 내 상대 위치를 보존한다. 브라우저가 이미 보정한 경우 남은 오차만 보정한다.
- 사용자가 상단 섹션을 보고 있으면 최신 글 위치를 맞추기 위해 화면을 강제로 이동시키지 않는다.
- 상세 복원 중에는 복원 작업이 스크롤을 소유한다. 동적 위치 보정이 동시에 별도 이동을 수행하지 않게 한다.
- 비동기 대기 후에는 최신 열 수·위치를 읽고, 취소·사용자 새 탐색 후 오래된 복원 작업이 다시 이동시키지 않게 한다.
- 직접 `?page=` 접근, 새 가상 sentinel 관찰, 모달의 남은 복원 표시를 재현한다. 위 핵심 수정 후에도 실패하면 해당 부분만 별도 변경으로 고친다.
- 기존 상세 복귀의 정렬 정책을 먼저 기록하여 유지한다. 이전 화면 좌표 보존으로 제품 동작을 바꾸려면 별도 정책 변경으로 표시한다.

## 5. C — Temporal 후처리 계약과 수정

주요 위치: [analytics.py](/Users/craigchoi/tem/src/is_temporal/analytics.py), [schedule.py](/Users/craigchoi/tem/src/pipeline_temporal/schedule.py), 필요한 workflow/runtime 및 시험.

### C1. 관측 간격과 랭킹 계산 조건을 맞춘다

현재 trends의 충분성 판단은 최근 30분 안의 알려진 조회수 관측 두 번을 요구하지만, T2 관측 offset은 3/24/48시간이다. 현재 입력으로 analytics만 실행해도 0건 또는 관측 부족 결과가 될 수 있다.

권장 기준은 급상승의 짧은 시간창을 유지하고, 대상 게시판/글의 제한된 범위에서 필요한 반복 관측을 확보하는 것이다. T2의 48시간 정책은 유지하며 T2 전체를 무조건 촘촘하게 수집하지 않는다. 관측 부족은 성공한 증가량 0과 구분해 기록한다. 대상 범위·관측 예산·coverage 분모를 확정한 뒤 구현한다.

### C2. 같은 window의 의존 순서를 보장한다

- 고정 window `W`와 입력 준비 조건을 모든 단계에서 공유한다.
- 고정 계산 window `W`와 웹 공개 시각 `P`를 구분한다. source의 MV 정의는 DB `now()`를 사용하므로 실제 view 정의를 확인하고, 지연 실행/과거 재계산에서 MV가 어느 시각의 결과를 공개하는지 명시한다. receipt의 `W`만으로 MV도 같은 window라고 인증하지 않는다.
- 현재처럼 같은 분에 독립 예약된 trends/MV와 rotation이 우연한 잠금 획득 순서에 의존하지 않게 한다.
- 권장 구현은 기존 analytics의 복합 stages 실행을 활용하여 `trends → MV → cluster_trends → rotation`을 같은 사이클에 연결하는 것이다. 별도 workflow가 필요하다면 단계 완료를 명시적으로 기다린다.
- cluster build/merge는 필요한 주기의 완료 결과와 연결한다. 모든 window에서 전체 build/merge를 강제로 실행하지 않는다.
- 대체되는 기존 예약과 새 사이클이 중복 실행되지 않게 전환한다. 관련 없는 NPS/CD와 모델/T0 운영 범위는 확대하지 않는다.
- 입력 준비에 시간 상한을 두고, 부족하면 partial/coverage 부족으로 기록한다. 오래된 window를 현재 시각으로 바꾸어 정상처럼 표시하지 않는다.
- 클러스터/rotation의 입력 시간 상한과 rank 갱신 대상도 확인한다. 현재 소스의 하한만 있는 조회와 전체 최신 rank 갱신은 정적 위험이므로, `W` 이후 입력이 있는 시험에서 재현한 뒤 필요한 부분을 수정한다.

### C3. 재시도와 새 입력 재계산을 구분한다

현재 receipt 키는 window·stages·IDs를 사용한다. 동일 window의 늦은 snapshot은 이전 결과를 재사용할 수 있고, stages 구성이 바뀌면 rotation이 재적용될 위험이 있다.

- 동일 입력 재시도는 같은 결과를 재사용하고 행/receipt/rotation 횟수를 늘리지 않는다.
- 늦은 입력은 입력 watermark 또는 계산 revision으로 구분해 같은 window를 필요한 만큼 재계산할 수 있게 한다. 실제 적용 방식은 격리 시험으로 결정한다.
- rotation의 소비 키는 stages 목록과 분리하여 window당 한 번만 반영한다.
- 이전 정상 결과를 오래된 재처리 결과가 덮어쓰지 않게 한다. 부분 실패·관측 부족·정상 빈 결과를 구분한다.
- 과거 window 재처리가 최신 rank·`last_shown_at`·suppression 상태와 공개 watermark를 뒤로 되돌리지 않게 한다.
- 가능한 한 기존 transaction과 upsert를 활용한다. 별도 공개 버전/테이블은 현재 transaction으로 일관성을 보장할 수 없는 경우에만 추가한다.

### C4. 건강 상태는 실제 결과로 판정한다

- worker liveness, Workflow 종료 상태, 업무 report 성공, 최신 window, coverage를 각각 기록한다.
- 최신 snapshots/trends/MV/cluster_trends의 시각과 후보 수를 확인한다.
- 기존 freshness의 10분 window age/완료 marker 기준을 유지하고, selected scope를 global SLA 통과로 표시하지 않는다.
- 입력이 실제로 없는 정상 빈 상태와 후처리 미실행·실패를 구분할 수 있는 결과를 남긴다.

## 6. D — 웹 갱신과 후속 데이터 연결

### 같은 섹션의 새 데이터

- 첫 페이지와 후속 JSON을 연결하는 데이터 세대의 출처·수명·전환 판단을 먼저 확정한다. 현재 `generatedAt`만으로 SSR 첫 페이지와 같은 세대라는 보장이 있다고 가정하지 않는다.
- 섹션/필터가 바뀌면 기존 정책에 따라 새 피드 상태로 초기화한다.
- 동일 데이터가 다시 전달되면 상태를 유지한다.
- 같은 데이터 세대의 새 첫 페이지는 ID 기준으로 갱신하면서 이미 추가한 페이지와 페이지 정보를 유지한다. 단순 `setPosts(initialPosts)`로 덮어쓰지 않는다.
- 데이터 세대가 바뀌면 이전 JSON 페이지/캐시를 그대로 섞지 않는다. 재검증/초기화 정책과 가능한 앵커 복구를 적용한다.
- 현재 글이 새 결과에서 제거되면 가까운 생존 글을 기준으로 위치를 잡고, 결과 전체가 비면 정상 빈 상태로 전환한다.
- 첫 페이지 ID·seen IDs·page map·page cursor·hasMore가 서로 일치하는지 검증한다.

### 후속 JSON 계약

- 첫 페이지는 SSR/주입 데이터이므로 `page-1.json`이 없어도 정상이다.
- producer와 consumer가 마지막 페이지/hasMore를 같은 의미로 사용하도록 맞춘다. 추가 데이터가 없으면 명시적으로 정상 종료한다.
- 추가 데이터가 있으면 page 2부터 마지막 페이지까지 실제 파일/응답, 필수 post 필드, 고유 ID, range/section 및 생성 버전을 검증한다.
- manifest만 있는 디렉터리를 데이터 생성 성공으로 인정하지 않는다. 현재 manifest의 `maxPages`와 클라이언트의 `lastPage` 차이도 정리한다.
- 새 generation의 manifest를 공개하기 전에 해당 페이지 파일이 준비되게 한다. 누락/지연 응답에도 기존 글을 보존하고 무한 재시도를 하지 않는다.
- JSON 생성/배포 계약은 가상화 수정과 별도 변경으로 검토한다. 운영 DB에 `build:data`를 반복 실행해 테스트 데이터를 만드는 방식은 사용하지 않는다.

### 정적 검사와 기존 시험

웹 기본 명령은 `pnpm test`, `pnpm exec tsc --noEmit`, `pnpm lint`이다. 현재 `lint`는 `next lint`이므로 첫 실행에서 도구·설정 유효성을 확인하고 기존 실패를 별도 기록한다. 도구 정리가 필요하면 작은 설정 변경으로 분리한다.

Temporal은 전용 fixture 연결을 설정한 뒤 `.venv/bin/python -m pytest tests/test_is_ingest.py tests/test_is_analytics.py tests/test_is_freshness.py tests/test_is_runtime.py tests/test_pipeline_contracts.py`를 실행한다. 변경 범위가 workflow/schedule로 이어지면 기존 `test_pipeline_temporal.py`·`test_pipeline_reliability.py`와 추가 순서/재시도 시험도 실행한다. 환경이 없어 skip된 DB/Temporal 시험은 통과로 세지 않는다.

계산 모델의 수정 조합은 실제 변경한 공통 좌표 함수와 연결해 시험한다. 기존 margin 0 또는 margin만 변경한 조합의 실패는 대조군 결과로 유지하며 앱 변경의 통과 결과와 구분한다. Workflow 정의를 바꾸면 기존 history replay와 pinned 입력/버전 호환성을 확인하고, worker가 새 코드를 읽었는지도 운영 전환에서 확인한다.

최종 `pnpm build`는 검증 DB/fixture 연결과 prerender의 업무 쓰기 가능성을 확인한 상태에서 실행한다. `build:main`/`build:data`도 업무 쿼리를 호출하므로 운영 DB를 브라우저 회귀 시험용으로 사용하지 않는다.

## 8. 최종 통과 기준

### 가상화

수치는 정지한 viewport에서 이벤트가 안정화된 후의 **CSS pixel** 기준 목표다. 계산 모델, 로컬 브라우저 fixture, 실제 기기 결과를 구분해 기록한다.

- 예상 가시 행/글 누락 **0건**, 중복 ID **0건**. sticky header 가림을 제외한 viewport와 실제 교차하는 글을 비교한다. overscan·활성 미리보기의 추가 DOM 행은 정상이다.
- 자동 모드 또는 실제 위치에 맞는 숫자 override에서 root 문서 좌표와 effective margin 차이 **1px 이하**, 행 배치 좌표 차이 **1px 이하**.
- 사용자가 목록을 읽는 상태에서 append/상단 높이 변화 후 같은 글의 화면 내 위치 오차 **2px 이하**. 문서 끝 clamp·의도적 사용자 이동은 따로 판정한다.
- 상세 복귀는 동일 글 ID와 기록한 정렬 정책의 목표 위치를 복원한다. 안정화 오차 **2px 이하**.
- 위치 변경/일반 append에서 불변 행 높이 캐시 유지. 열 수/카드 모양 변경에는 적절한 재측정.
- 유한 로컬 fixture의 입력/리소스 반영 종료 후 **2초 이내** 레이아웃 안정화, 계속되는 측정·스크롤 보정 반복 없음. 네트워크·집계 완료 SLA와 별개다.
- 빠른 스크롤 동선에서는 지속적인 빈 영역·위로 돌아왔을 때의 글 누락·반복 앵커 이동이 없어야 한다. 모든 중간 프레임의 즉시 렌더를 보장한다는 뜻은 아니다.
- 긴 피드에서 DOM 행 수가 전체 글 수에 비례해 늘어나지 않음. 활성 미리보기 유지 행은 별도 집계한다.
- Chrome의 desktop/mobile viewport를 자동 검증하고 실제 지원 Safari 및 모바일 브라우저에서도 빠른 스크롤·폭 변경·뒤로 복귀를 확인한다. viewport 흉내를 실제 모바일 검증으로 표시하지 않는다.

### 데이터 및 운영

- synthetic 입력은 기대값까지 대조하고 실제 최신 입력은 원본→snapshots→trends→MV→cluster_trends→웹 결과가 연결됨을 확인한다.
- 충분한 후보가 있는 시험에서는 기대 상단 카드가 표시됨. 후보가 없는 시험에서는 정상 빈 상태로 종료됨.
- 동일 입력 재시도·중복 실행의 업무 결과 중복 **0건**, late input 재계산 가능, rotation 중복 반영 **0건**.
- 제한 운영은 최소 **3개 연속 10분 window**를 관측한다. 최신성·coverage·partial/failure·backlog·요청 예산을 함께 판정한다.
- 24시간 연속성은 실제 24시간 관측 후, T2 48시간 완료는 실제 48시간 관측 후 각각 인증한다. 이를 코드 시험 통과와 별도 기록한다.
- 선택 게시판 성공을 전체 게시판/모델/global SLA 성공으로 확대하지 않는다. 미검증 대상은 명시한다.

## 9. 인수와 rollback

최종 보고서에는 변경 diff, 실행 환경/버전, 시험 명령과 결과, 브라우저별 동선, 입력 window와 DB 결과, 실제 웹 표시 ID, 운영 관측 범위, 미검증 항목을 포함한다. 증거 없이 모든 항목을 체크하지 않는다.

웹은 가상화·갱신·JSON 계약을 나눈 변경 단위로 되돌릴 수 있게 한다. Temporal은 새 예약/잡과 입력 watermark·계산 revision을 기록하고, 문제가 생기면 새 예약 pause → 실행/lease 소유권 확인 → 필요한 worker 정리 → 호환성 확인 순으로 복구한다. 검증된 이전 결과를 보존하고 전체 업무 DB 초기화나 무조건적인 옛 writer 동시 재개는 하지 않는다.

코드 수정 완료, 제한 실제 경로 통과, 장기 운영 확인을 세 가지 상태로 별도 보고한다. 라이브러리 업데이트는 이 수정의 기준 결과가 확보된 뒤 별도 변경으로 진행한다.
